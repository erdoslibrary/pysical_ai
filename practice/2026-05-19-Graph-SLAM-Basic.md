# Graph SLAM 기초 — 왜 필요하고 무엇을 하는가

> 대응 실습 파일: `11.01.SLAM-Basic.ipynb`

---

## 핵심 질문: 왜 SLAM이 필요한가?

로봇은 자신이 어디 있는지 알아야 움직일 수 있습니다.  
그런데 로봇이 위치를 추정하는 두 가지 방법은 각각 치명적인 한계를 가집니다.

| 방법 | 설명 | 한계 |
|------|------|------|
| **오도메트리(Odometry)** | 바퀴 회전수로 이동 거리 계산 | 오차가 누적되어 갈수록 틀려짐 (Drift) |
| **LiDAR/카메라** | 주변 환경을 직접 관측 | 지도가 없으면 자신의 위치를 알 수 없음 |

**SLAM(Simultaneous Localization and Mapping)** 은 이 두 문제를 동시에 푸는 알고리즘입니다.  
"지도를 만들면서 동시에 내 위치도 찾는다."

---

## Step 1: 시뮬레이션 환경 — 왜 방 안인가?

실습은 로봇이 5×5m 방 안에서 사각형 경로를 도는 시나리오를 사용합니다.

**이 설정이 중요한 이유:**
- 방 안은 **벽과 장애물이 고정**되어 있어 LiDAR 측정 결과를 예측할 수 있습니다.
- 로봇이 **출발점으로 돌아오는 경로(Loop)**가 있어야 Loop Closure를 실습할 수 있습니다.
- 실제 ROS2 환경의 복잡성을 제거하고 **SLAM의 수학적 원리에만 집중**할 수 있습니다.

---

## Step 2: 2D Pose와 변환 행렬 — 왜 행렬로 표현하는가?

로봇의 위치는 $(x, y, \theta)$ 세 값으로 표현됩니다.  
이걸 단순 숫자로 더하면 안 됩니다. **각도가 있기 때문입니다.**

### 핵심 개념: Homogeneous Transform (동차 변환)

$(x, y, \theta)$를 3×3 행렬로 변환하면 **회전과 이동을 행렬 곱 하나로** 표현할 수 있습니다.

```
T = | cos θ  -sin θ  x |
    | sin θ   cos θ  y |
    |   0       0    1 |
```

**이렇게 해야 하는 이유:**
- 여러 이동을 누적할 때 `T1 @ T2 @ T3 ...`처럼 행렬 곱으로 간단하게 계산됩니다.
- 상대 위치 계산이 `inv(T1) @ T2`로 명확해집니다.
- ROS2, OpenCV, 로보틱스 전반에서 표준으로 쓰이는 표현법입니다.

### 실습에서 정의하는 함수들

| 함수 | 역할 |
|------|------|
| `v2t(v)` | `[x, y, θ]` → 3×3 행렬로 변환 |
| `t2v(T)` | 3×3 행렬 → `[x, y, θ]`로 역변환 |
| `pose_compose(xi, xj)` | 두 Pose 누적 (`xi ⊕ xj`) |
| `relative_pose(xi, xj)` | xi에서 xj까지의 상대 위치 |
| `noisy_odometry(delta)` | 실제 이동에 가우시안 노이즈 추가 |

## Step 3: Ground Truth vs Odometry Drift — 문제를 직접 확인

로봇이 정사각형을 한 바퀴 돌고 돌아왔을 때:

- **Ground Truth**: 출발점과 정확히 일치해야 합니다.
- **Odometry**: 매 스텝마다 25% 노이즈가 쌓여서 출발점에서 벗어나 있습니다.

**왜 이 비교를 보여주는가:**  
SLAM이 해결해야 할 문제가 얼마나 심각한지를 시각적으로 보여줍니다.  
오차는 거리가 늘어날수록 **선형이 아니라 지수적으로** 커지기 때문에,  
큰 공간이나 긴 시간 운행에서는 오도메트리만으론 사용이 불가능합니다.

---

## Step 4: Pose Graph 구성 — SLAM의 수학적 모델

Graph SLAM은 로봇 경로를 **그래프**로 모델링합니다.

```
Node(0) --[odom]--> Node(1) --[odom]--> ... --[odom]--> Node(N)
   ↑_______________________[Loop Closure]________________________|
```

### Node (노드)
- 각 시점에서 로봇의 추정 Pose `(x, y, θ)`
- 처음엔 오도메트리로 초기화됨 (틀린 값이지만 최선의 초기 추정치)

### Edge (엣지)
두 Node 사이의 **측정된 상대 위치 + 신뢰도(Information Matrix)**

| 엣지 종류 | 데이터 출처 | 신뢰도 |
|----------|-----------|--------|
| **Odometry Edge** | 바퀴 인코더 | 상대적으로 낮음 (노이즈 25%) |
| **Loop Closure Edge** | LiDAR Scan Matching | 높음 (노이즈 2%) |

### Information Matrix (정보 행렬) — 왜 필요한가?

단순히 측정값을 평균 내면 신뢰도가 높은 측정값과 낮은 측정값이 동일하게 취급됩니다.  
Information Matrix = 공분산의 역행렬로, **신뢰도가 높은 측정값에 더 큰 가중치**를 줍니다.

```python
info_odom = np.diag([1/(0.05**2), 1/(0.05**2), 1/(0.02**2)])  # 오도메트리 (낮은 신뢰)
info_lc   = np.diag([1/(0.03**2), 1/(0.03**2), 1/(0.01**2)])  # 루프 클로저 (높은 신뢰)
```

## Step 5: LiDAR Scan & Occupancy Map — Drift가 지도를 어떻게 망치는가

같은 LiDAR 측정값이라도, 로봇이 자신의 위치를 **어디라고 믿느냐**에 따라  
전혀 다른 지점에 포인트를 찍게 됩니다.

```
실제 측정: 로봇 기준 좌표계에서 (lx, ly)

GT 기반 지도:   world_point = T_gt   @ [lx, ly, 1]  → 선명한 벽
Odom 기반 지도: world_point = T_odom  @ [lx, ly, 1]  → 흐릿하고 겹치는 벽
```

**이게 왜 중요한가:**  
Drift가 있는 오도메트리로 만든 지도는 벽이 두꺼워지고 장애물이 흐릿하게 보입니다.  
이런 지도로 경로 계획을 하면 로봇이 실제로 없는 장애물을 회피하거나  
실제 있는 벽에 부딪히는 문제가 생깁니다.

---

## Loop Closure — SLAM이 오차를 수정하는 원리

루프를 돌고 돌아왔을 때 "여기가 시작점이다"라는 걸 인식하면,  
그 정보(Loop Closure Edge)를 그래프에 추가하고 **전체 그래프를 최적화**합니다.

```
최적화 목표: 모든 Edge의 측정값과 Node 위치의 불일치(오차)를 최소화

cost = Σ (z_ij - h(xi, xj))ᵀ · Ω_ij · (z_ij - h(xi, xj))
                                  ↑
                           Information Matrix (신뢰도 가중치)
```

이 최적화가 끝나면 오도메트리로 인해 흩어진 Node들이  
Loop Closure의 제약에 맞게 **재배열**됩니다.

## 전체 흐름 요약

```
[오도메트리 드리프트 발생]
        ↓
[Pose Graph 구성: Node + Odometry Edge]
        ↓
[LiDAR Scan Matching으로 Loop Closure 감지]
        ↓
[Loop Closure Edge 추가]
        ↓
[Graph Optimization (최소 제곱법)]
        ↓
[보정된 Pose → 깨끗한 지도 생성]
```

## ROS2와의 연결

실제 ROS2 환경에서 이 파이프라인은 다음 패키지들이 담당합니다:

| 역할 | ROS2 패키지 |
|------|------------|
| Pose Graph 최적화 | `slam_toolbox`, `cartographer` |
| LiDAR Scan Matching | `laser_scan_matcher` |
| 오도메트리 | `robot_localization` (EKF 기반) |
| 지도 저장/불러오기 | `nav2_map_server` |

이 실습은 그 내부에서 수학적으로 무슨 일이 일어나는지를 직접 구현해본 것입니다.
